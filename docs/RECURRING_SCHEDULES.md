# 循環排程與多分類採集

## 使用方式

開啟 http://127.0.0.1:8012/schedules ，選「新增排程」。

1. 填名稱、資料來源，選每日、每週指定星期或指定日期僅一次。
2. 設定台灣執行時間及開始日期。循環可填結束日期；留空持續有效，但仍受額度限制。
3. 填分類名稱、關鍵字及每分類最多商品數（1–2）；可增加分類欄位，最多 20 分類。順序數字決定執行順序。同順序依表單列順序。移除分類需清空名稱、關鍵字與件數。
4. 預覽接下來 5 次及未來 30 天請求估計，再確認儲存。儲存不採集；「立即執行一次」另行確認。

每列代表一個規則，不需逐日新增。查看／編輯可暫停、恢復或封存。封存不可恢復，需另建規則；既有歷史仍保留。清單管理所有來源，各列標示模擬或真實資料。來源切換導覽不會將模擬規則改成真實來源。

## 執行與額度

- Python 排程器每 10 秒檢查；背景任務執行器依序處理所有分類，完成後產生本次報表。電腦須開機、兩個程序須正常。規則啟用與程序在線是不同狀態。
- 新增從確認後的下一個未來時間開始；同日未來時間可用。編輯不改已完成紀錄或正在執行的版本，取消尚未開始的舊版本任務。
- 暫停期间跳過，不補抓。未派發且已超過 15 分鐘容許時間的安排記錄漏跑；已入列任務不因等候其他任務而漏跑。
- 同時到期按預定時間、規則 ID 排隊。每次唯一識別由規則 ID 及預定 UTC 時間決定，版本更新不繞過去重。
- 每分類预估一次搜尋加商品明細次數。兩分類各 2 件＝預估 6 次，超過目前每日 5 次。可減少每類件數或拆成不同天。
- 保留此 DB 累計 30 次、UTC 每日 5 次。台灣 08:00 重置每日帳本，累計不自動重置。不可將此帳本視為 RapidAPI 帳號剩餘。
- 整次原子性預留額度，與 CLI／手動任務共用鎖及帳本。來源金鑰及免費硬上限確認、供應商最近觀測估計亦需通過。供應商未知時不自動呼叫來查餘額。
- 未來 30 天為預測，不永久預留。保存可有用量警示，到期不足則整次不送出請求。外部入口消耗供應商次數可能使估計過時。
- 供應商失敗停止剩餘分類，已取得資料保留，無自動付費重試。重啟不重送執行中的請求；可從已成功批次重產報表。

## 結果、報表與歷史

每次執行可看各分類批次與商品來源，並下載綜合 Excel。分頁為執行說明、分類結果、商品明細、留存來源。全部分類成功為完整，否則標示不完整；未取得的分類不使用較舊資料填補。同 ASIN 出現在不同分類時，各批次觀測各自保留，不把它們當不同商品來推算全市場。

Excel 保留框線、原始來源欄位、價格與累計評價數。來源 JSON 不是人工評論；不新增人工或 AI 情緒判斷。評價數不是本期新增評論數，不代表銷量或銷售額。輸出讀回核對通過後登錄雜湊，下载再次核對。重產使用原執行的成功批次 ID，不抓供應商，不覆寫舊檔。

報表中心另列多分類排程報表，與原累計報表區分。新執行頁顯示最近 100 次；完整執行紀錄仍保留於 DB。規則編輯頁保留設定版本。舊安排與版本在「轉換前的安排」唯讀查閱。

## 切換及可攜性

使用 `gummy schedule-migrate` 在 admission、schedule-control、collection 三把鎖下，將原計畫尚未執行且未過期的日期轉為單次規則。需無排隊或執行中任務／採集。轉換可重複呼叫，不重建規則、不抓資料、不改原計畫檔。

資料表以新增方式加入：`recurring_control`、`recurring_rules`、`recurring_versions`、`recurring_occurrences`。新增工作型別 `schedule`、`schedule-report`，沿用現有任務與額度帳本。切換後 Python 不再派發原逐日採集／定時報表；舊 `run-plan`、`scheduled-collect` 也拒絕執行。原報表仍可讀取。

排程表單沿用本機來源限制、登入保護（若有設定）、session 綁定簽章、5 分鐘有效確認和 CSRF 檢查。`/v1/plan` 新增 `recurrence`，提供規則、下次時間、30 天預覽與最近歷史；`legacy_batches` 保留舊安排。編輯介面不接受任意路徑或命令。

部署需先完成 DB 備份並停止舊排程與 worker，再切換、重啟新版服務；不能讓不懂切換標記的舊程式同時執行。若需退版，先停所有採集程序，再由管理者核對備份後新增資料與請求帳本，不能直接還原舊額度資料庫導致重複消耗。

仍為本機版本；macOS 服務驗證不等於 Windows／Linux 常駐或雲端部署驗收。搬移需連同 DB、原計畫、設定、排程狀態及 exports，金鑰另行安全配置。平台本身不依賴 Codex。
